## 数据库迁移与发布要求

迁移 16 新增 t_background_job 和 t_admin_user.session_version；不修改既有业务字段内容。使用项目原有发布流程，先备份并在 migrate profile 中执行 aerich upgrade，再切换后端镜像。不能只更新 Python 文件而跳过迁移。

生产 JWT_SECRET 需至少 32 字节。新权限边界意味着运营账号不能直接编辑已发布内容，需要发布者先撤回草稿或授予对应发布权限。

## 后台任务运行语义

- worker 每 5 秒轮询，一次最多取 20 个任务。以数据库条件更新抢占任务，租约 300 秒；进程退出后，过期租约可重新领取。
- 询盘提交接口先返回 PENDING。未配置 SMTP 时每 5 分钟延后，不消耗失败次数；不会自动补发迁移前没有任务记录的旧询盘。
- 失败任务以 60、120、240、480 秒等间隔退避，最多 5 次失败尝试后保留 FAILED；邮件失败同步进入既有通知。
- 成功任务删除；失败任务仅保存错误类型，避免日志或错误字段存入凭据。
- 邮件为至少一次投递。SMTP 服务端已接收、但进程在记录 SENT 前退出时，重试可能产生重复通知；不能保证跨 SMTP 和数据库的严格一次投递。
- 缓存任务提交后会立即尝试执行；Redis/官网不可达时保留任务重试。FAILED 任务需要处理原因后重新入队，不能把失败日志当作修复完成。

只读查看失败任务：

~~~sql
SELECT id, kind, attempts, last_error, created_time
FROM t_background_job
WHERE status = 'FAILED'
ORDER BY id DESC;
~~~

确认故障已修复后，可由运维针对已确认的任务 ID 将 status 设为 PENDING、attempts 设为 0、lease_token 清空、available_at 设为 CURRENT_TIMESTAMP。不要批量重试未经核实的邮件任务。

## 后续优化方向

1. 使用实际慢查询与流量数据决定复合索引和缓存策略，避免在没有证据时增加索引及运维复杂度。
2. 把失败任务数量、最老待处理任务年龄、调度延迟、邮件失败率接入现有监控；当前提供持久化记录、日志和邮件失败通知。
3. 多机部署前再落实共享媒体存储和 CDN。当前媒体仍是本地卷，独立应用副本不会自动共享磁盘。
4. 版本恢复仍覆盖核心内容字段，不包含完整图库/规格历史；若业务要求完整资产回滚，需要明确新的版本范围。
5. 内容与缓存之间采用最终一致性。并发读取回填旧缓存的极小时间窗口、长时间依赖故障后的人工任务处理仍需结合实际 SLA 设计。
